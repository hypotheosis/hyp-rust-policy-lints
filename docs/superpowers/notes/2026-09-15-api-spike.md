## 1. What crate name the expansion chain reports for `#[hegel::test]`

**Observed: `hegel_macros`. Nothing else.**

Raw probe output for the hegel test:

```
PROBE test fn: tests::prop
PROBE   expn crate: hegel_macros (kind Macro(Attr, "hegel::test"))
```

The expansion chain for a `#[hegel::test]` function is exactly **one** frame deep.
That frame's `macro_def_id.krate` resolves to crate name `hegel_macros`.

### Why, and why it is stable

`tcx.crate_name(krate)` returns the crate's **`[lib] name`**, taken from its own
metadata. It is *not* the Cargo package name, and it is *not* whatever the consumer
aliased the dependency to. For the real crates:

| Cargo package (crates.io) | `[lib] name` → what `tcx.crate_name` reports |
|---|---|
| `hegeltest` 0.14.27 | **`hegel`** |
| `hegeltest-macros` 0.14.27 | **`hegel_macros`** |

Verified directly in the vendored manifests under
`~/.cargo/registry/src/index.crates.io-*/hegeltest-0.14.27/Cargo.toml` (`[lib] name = "hegel"`)
and `hegeltest-macros-0.14.27/Cargo.toml` (`[lib] name = "hegel_macros"`).

Because `crate_name` reads the *defining* crate's own lib name, a consumer cannot
change it by renaming the dependency. This was tested, not assumed:

- Dep declared as `hegel = { package = "hegeltest", version = "0.14" }` → reported `hegel_macros`.
- Dep declared as plain `hegeltest = "0.14"` → reported `hegel_macros`.

**PLAN CORRECTION (affects Tasks 4, 6, 8).** The plan declares

```rust
const HEGEL_CRATE_NAMES: &[&str] = &["hegel", "hegeltest", "hegeltest_macros"];
```

This is wrong in both directions. `hegel_macros` — the only name the expansion chain
ever actually reports — is **absent**, so `non_hegel_test` would fire on *every* real
hegel test. And `hegeltest` / `hegeltest_macros` are package names that
`tcx.crate_name` can never return. The correct constant is:

```rust
/// `tcx.crate_name` reports a crate's `[lib] name`, not its Cargo package name.
/// The `hegeltest` package's lib is named `hegel`; the `hegeltest-macros`
/// package's lib is named `hegel_macros`. Neither is affected by how a consumer
/// renames the dependency in its `Cargo.toml`.
const HEGEL_CRATE_NAMES: &[&str] = &["hegel", "hegel_macros"];
```

`hegel` is retained for the Task 4 body-scan fallback (the non-macro builder form,
whose types resolve into the runtime crate). The expansion-chain walk alone only
ever needs `hegel_macros`.

### Do not match on `ExpnKind`'s macro path string

The probe also printed `kind Macro(Attr, "hegel::test")`. That string is the path
**as written at the call site**, so it reflects the user's aliasing and is not
trustworthy. Match on `crate_name(macro_def_id.krate)`, as the plan already does.

### Corollary: `#[hegel::test]` is unhygienic, and that constrains the Task 6 stub

The macro expands to absolute `hegel::...` paths. If the crate is not in scope under
precisely the name `hegel`, expansion fails. Observed by aliasing the dep to
`zzz_weird_alias`:

```
error[E0433]: cannot find module or crate `hegel` in this scope
  = note: this error originates in the attribute macro `zzz_weird_alias::test`
```

**PLAN CORRECTION (affects Tasks 6 and 8).** Two consequences:

1. The plan's fixture line `use hegeltest as hegel;` **does not compile**. Cargo binds
   a dependency under its `[lib] name` (or its rename key), so with `hegeltest = "0.14"`
   the extern crate is already `hegel` and the name `hegeltest` does not exist:
   `error[E0432]: unresolved import hegeltest`. Fixtures should just write `hegel::`
   directly. The `hegel = { package = "hegeltest" }` rename in a consumer manifest is
   harmless but redundant — it resolves to the same name the lib already has.
2. The Task 6 stub crates must set their **`[lib] name`**, not just their package name,
   to `hegel` and `hegel_macros`. A stub package named `hegeltest` whose lib name
   defaults to `hegeltest` would report a crate name that never occurs in reality, and
   the UI tests would be validating a name the production lint must not match.

## 2. `lint_level_at_node`: exact return type and destructuring

**PLAN CORRECTION (affects Tasks 5 and 7): `tcx.lint_level_at_node` does not exist on
this nightly, and neither does `LevelAndSource`.** Both shapes the plan anticipated are
wrong. The method has been renamed and the struct's `level` field is now private.

### The real API

Defined in `compiler/rustc_middle/src/lint.rs` (available locally at
`$(rustc +nightly-2026-07-09 --print sysroot)/lib/rustlib/rustc-src/rust/compiler/rustc_middle/src/lint.rs`):

```rust
impl TyCtxt<'_> {
    pub fn lint_level_spec_at_node(self, lint: &'static Lint, id: HirId) -> StableLevelSpec;
}

pub type StableLevelSpec = LevelSpec<StableLintExpectationId>;

pub struct LevelSpec<Id = LintExpectationId> {
    level: Level,           // PRIVATE — read it with `.level()`
    lint_id: Option<Id>,    // PRIVATE — read it with `.lint_id()`
    pub src: LintLevelSource,
}

impl<Id: Copy> LevelSpec<Id> {
    pub fn level(self) -> Level;
    pub fn is_allow(self) -> bool;   // convenience: level == Level::Allow
    pub fn lint_id(self) -> Option<Id>;
}
```

`LevelSpec` is `Copy`, so `.level()` by value costs nothing and does not move `.src`.

### Imports

```rust
use rustc_middle::lint::LintLevelSource;   // exact path, unchanged from the plan
use rustc_session::lint::Level;
```

`lint_level_spec_at_node` is an inherent method on `TyCtxt`, brought in by
`extern crate rustc_middle;` — no trait import needed.

### The shape Tasks 5 and 7 should write

Replace the plan's

```rust
let level = cx.tcx.lint_level_at_node(NON_HEGEL_TEST, hir_id);
match level {
    (Level::Allow, LintLevelSource::Node { reason: Some(_), .. }) => {}
    (Level::Allow, LintLevelSource::Node { span: attr_span, .. }) => { /* report */ }
    _ => {}
}
```

with

```rust
let spec = cx.tcx.lint_level_spec_at_node(NON_HEGEL_TEST, hir_id);
match (spec.level(), spec.src) {
    // Exempted in source with a stated reason: accepted.
    (Level::Allow, LintLevelSource::Node { reason: Some(_), .. }) => {}

    // Exempted in source with no reason: report the attribute.
    (Level::Allow, LintLevelSource::Node { span: attr_span, .. }) => { /* report */ }

    _ => {}
}
```

Only the first line changes; the match arms the plan already wrote are correct as-is,
because `spec.src` destructures exactly as the plan assumed.

### `LintLevelSource` is unchanged and `reason` is genuinely reachable

```rust
pub enum LintLevelSource {
    Default,
    Node { name: Symbol, span: Span, reason: Option<Symbol> },
    CommandLine(Symbol, Level),
}
```

The `reason: Option<Symbol>` field exists, is public, and is populated. Both the
populated and empty cases were observed, using a test carrying
`#[allow(hyp_probe, reason = "...")]` and one carrying a bare `#[allow(hyp_probe)]`:

```
PROBE test fn: tests::allow_with_reason
PROBE   spec debug: LevelSpec { level: Allow, lint_id: None, src: Node { name: "hyp_probe", span: src/lib.rs:8:13: 8:22 (#0), reason: Some("probing the reason field") } }
PROBE   ALLOW via Node name=hyp_probe reason=Some("probing the reason field") attr_span=src/lib.rs:8:13: 8:22 (#0)

PROBE test fn: tests::allow_bare
PROBE   spec debug: LevelSpec { level: Allow, lint_id: None, src: Node { name: "hyp_probe", span: src/lib.rs:14:13: 14:22 (#0), reason: None } }
PROBE   ALLOW via Node name=hyp_probe reason=None attr_span=src/lib.rs:14:13: 14:22 (#0)

PROBE test fn: tests::plain
PROBE   spec debug: LevelSpec { level: Warn, lint_id: None, src: Default }
```

Three things worth noting for Task 5:

- The `span` in `LintLevelSource::Node` covers **just the lint name inside the
  attribute** (`8:13: 8:22` is the 9 columns spelling `hyp_probe`), not the whole
  `#[allow(...)]` attribute. That is the right span to point the
  `hegel_exemption_without_justification` diagnostic at, but the plan's local name
  `attr_span` is slightly misleading — it is the lint-name span.
- An `allow` written on an enclosing module or item is found too: the query walks up
  the HIR parent chain (`probe_for_lint_level_spec` in `rustc_middle/src/lint.rs`). So
  the exemption check works whether the attribute sits on the test fn, its `mod tests`,
  or the crate root. Observed with `#[allow(hyp_probe, reason = "module-level
  exemption")]` on `mod tests` and a bare `#[test] fn` inside it:

  ```
  PROBE test fn: tests::inherits_module_allow
  PROBE   spec debug: LevelSpec { level: Allow, lint_id: None, src: Node { name: "hyp_probe", span: src/lib.rs:2:9: 2:18 (#0), reason: Some("module-level exemption") } }
  ```

  Note the span points at the *module's* attribute (line 2), not the test function.
  That is correct behaviour, but it means a whole `mod tests` can be exempted with one
  justified `allow` — worth a deliberate UI-test case in Task 5, and worth deciding
  whether that breadth is intended policy.
- A test with no attribute yields `src: Default` and the lint's declared default level,
  so the `_ => {}` arm handles it and no special-casing is needed.

**Declare `NON_HEGEL_TEST` at `Warn` or `Deny`, not `Allow`** *(INFERRED, not observed
— the probe was switched to `Warn` before the run and the `Allow` default was not
re-tested).* The task's original probe declared the lint at `Allow`. With an `Allow`
default, an unexempted test and an exempted one both report `Level::Allow`, and the
only thing separating them is `src` (`Default` vs `Node`). The match above is written
to be correct either way, because its exemption arms require `LintLevelSource::Node` —
but declaring the lint at `Warn` keeps the two cases distinguishable by `Level` alone
and is what the probe actually ran with.

## 3. The `def_path_str` of the test-descriptor type

**Observed: `tests::test::TestDescAndFn`** — one per `#[test]`, including the hegel one.

```
PROBE const ty: tests::test::TestDescAndFn
PROBE const ty: tests::test::TestDescAndFn
PROBE const ty: tests::test::TestDescAndFn
PROBE const ty: tests::test::TestDescAndFn
```

The leading segment is the **enclosing module of the test** (here `mod tests`), so the
path varies per crate and per module — it is *not* a fixed `test::TestDescAndFn`.
This is exactly why the plan's `ends_with("TestDescAndFn")` substitution for
`dylint_internal::match_def_path(cx, ty_def_id, &paths::TEST_DESC_AND_FN)` is the right
call: a prefix or equality match would fail. `ends_with("TestDescAndFn")` is confirmed
correct and is what `test_fns.rs` now ships.

Four `#[test]`-derived constants were found for four test functions, and
`find_test_fns` recovered all four `DefId`s, **including the `#[hegel::test]` one**:

```
PROBE test fn: tests::plain
PROBE test fn: tests::allow_with_reason
PROBE test fn: tests::allow_bare
PROBE test fn: tests::prop
```

That last line is the load-bearing one for Tasks 3-7: `#[hegel::test]` ultimately
expands to an ordinary `#[test]`, so the `TestDescAndFn` recovery walk sees hegel tests
and plain tests alike, and the hegel/non-hegel decision really can be made afterwards
from the expansion chain.

`ItemKind::Const(_ident, _generics, ty, ConstItemRhs::Body(body_id))`, `hir_free_items`,
`hir_item`, `hir_body`, and `clippy_utils::res::MaybeResPath::basic_res` all exist with
the shapes the plan's reconstruction used. The only correction: `MaybeDef` is **not**
needed — `opt_def_id()` is inherent on `rustc_hir::def::Res`, and importing `MaybeDef`
trips the crate's `unused_imports` warning.

## 4. Does `hegeltest` 0.14 build on nightly-2026-07-09?

**Observed: yes.** `hegeltest` resolves to **0.14.27** (latest in the 0.14 line; latest
overall is 0.45.3). `cargo +nightly-2026-07-09 test --no-run` compiled it, its
`hegeltest-macros` 0.14.27 proc-macro crate, and all 38 transitive dependencies with
no errors and no warnings from hegel itself.

The only warnings emitted were the expected `unknown lint: hyp_probe` from the probe's
own `#[allow(hyp_probe)]` attributes, which appear under plain `cargo` because the
dylint driver is not loaded. Under `cargo dylint` the lint is registered and the
warnings disappear — confirming that a consumer can write `#[allow(non_hegel_test)]`
and see it honoured under dylint, while plain `cargo build` merely warns
`unknown_lints` (a warning, not an error). Task 8's e2e fixtures should expect that
warning in non-dylint builds, or set `#![allow(unknown_lints)]`.

So the plan's contingency ("if `hegeltest` fails to build on this nightly, drop it and
rely solely on the stub") does **not** apply. The real crate can be used directly in
the Task 8 e2e fixtures, and the stub in Task 6 is needed only to keep UI tests off the
network.

## How to re-run this probe

The probe lint (`HYP_PROBE`, `Probe` in `lints/hyp_hegel/src/lib.rs`) and
`test_fns::probe_const_type_paths` are temporary and are deleted in Task 3.

```bash
cd lints && cargo build
cd /path/to/scratch/crate
DYLINT_LIBRARY_PATH=/abs/path/to/lints/target/debug cargo dylint --all -- --all-targets 2>&1 | grep PROBE
```

`--all-targets` is mandatory. Without it no test harness is generated, no
`TestDescAndFn` constants exist, `find_test_fns` returns empty, and the probe prints
nothing at all — which is indistinguishable from success.
